# Github Fork同步/看板工具

> 一次扫描，看清所有 fork 谁落后了；勾选、批量快进，支持暂停 / 停止 / 取消。

![version](https://img.shields.io/badge/version-1.1.0-blue)
![license](https://img.shields.io/badge/license-MIT-green)
![dependencies](https://img.shields.io/badge/dependencies-0-brightgreen)

一个纯前端的单文件网页工具：填入 GitHub 令牌，扫描你账号下的**全部仓库**，自动区分 fork 与自建，把落后的 fork 一键快进到上游。不用安装、不用后端、不用 clone。

---

## 为什么做这个

GitHub 自带的 **Sync fork** 一次只能点一个仓库。当你 fork 了几十个项目（我这个账号有 153 个 fork），逐个点开、对比、同步是不现实的。

这个工具把整个流程压缩成三步：

```
粘贴令牌  →  扫描全部仓库  →  勾选 → 开始同步
```

而且它知道**哪些该同步、哪些不该**：自建仓库不参与，分叉过的 fork 不硬来，模板衍生的仓库直接判定为"无关历史"。

## 亮点

### 1. 单文件、零依赖、双击即用

整个工具就是一个 `index.html`（约 64 KB），没有构建步骤、没有 npm、没有后端。双击打开，或者丢到 GitHub Pages 上就是一个在线工具。

### 2. 登录即扫描，自动分清 fork 与自建

填入令牌后一次拉取全部仓库（支持分页，实测 174 个仓库 2 次请求读完），按 `fork` 字段自动分组：

- **fork** → 进入检测队列，逐个查上游、算差距
- **自建** → 单独折叠展示，完全不参与同步

不需要手动维护仓库清单。

### 3. 精确判定，不是靠提交数猜的

对每个 fork 走三次判定：

| 步骤 | 请求 | 作用 |
|---|---|---|
| 1 | `GET /repos/{fork}` | 取 `parent`，拿到真正的上游 |
| 2 | `GET /repos/{upstream}/compare/{upBranch}...{owner}:{branch}` | 一次拿到「落后几个」+「独有几个」 |
| 3 | 404 判断 | 没有共同祖先 = 模板衍生，标记为无法同步 |

跨 fork 的 compare 能正确处理「fork 上有自己的提交」的情况——不会把分叉误判成无关历史。

### 4. 分页 + 多选 + 全选筛选结果

- 每页 50 个，底部翻页
- 每张卡片一个复选框，选择**跨页保留**
- 「全选本页」or「全选筛选结果」（一次选中当前筛选下的全部）
- 状态筛选：需要跟进 / 可快进 / 分叉 / 检测失败 / 同步失败 / 无法判定 / 已是最新 / 全部

153 个 fork 也能有条理地处理。

### 5. 批量任务完全可控

不是"点一下然后祈祷"：

| 按钮 | 行为 |
|---|---|
| **开始同步 (N)** | 确认后按队列逐个同步，实时显示进度与当前仓库 |
| **暂停 / 继续** | 当前这条跑完后停住，不再开新的；再点继续接着跑 |
| **停止** | 当前这条完成后结束整批，未处理的项目**保持勾选**，可再次开始 |
| **取消** | 立刻 `AbortController.abort()` 中断当前请求并清空队列；被中断的那条会自动复查真实状态 |

> 取消用的是真中断，不是"假装停下"——已经被服务端执行的合并会被复查出来。

### 6. 失败可追踪、可重试

- 失败原因写在卡片上，并随缓存持久化
- 顶部汇总：`上次同步：成功 48 · 失败 2 · 缺 workflow 权限 3`
- 一键筛选「同步失败」
- 失败项保持勾选，修好权限后直接重试

### 7. 专门处理 workflow 权限这个坑

同步内容里一旦包含 `.github/workflows/*`，GitHub 会要求令牌具备 `workflow` 权限，否则**整次同步被拒**。

工具会：

- 识别这条错误，翻译成「令牌缺少 Workflows 权限」而不是含糊的 403
- 卡片上给出「怎么加」分步说明 + 「去网页同步」兜底入口
- 顶部芯片统计受影响项目数
- 批量同步遇到第一个此类失败时**自动暂停**，不让后面几十个依次失败
- 顶部常驻令牌自检：显示令牌类型（细粒度 / classic）和 fingerprint，classic 还会直接读出 scopes 并标红缺失项

### 8. 非 fork 的副本也能同步

有些仓库是从模板生成的、或者 clone 后重新推的，GitHub 不给 fork 关系，也就没有 Sync fork 按钮。

对这类"手动纳入"的副本，工具会：

1. 先在当前 HEAD 上打一个 `pre-sync-<时间戳>` 的备份 tag
2. 再把分支强制指向上游 HEAD

前提是它没有独有提交（ahead = 0），所以这一步是无损的。

### 9. 忽略名单

不想看的仓库可以批量移除，进入底部的「已忽略」，下次扫描自动跳过，随时可以恢复。

### 10. 隐私优先

- 没有后端，没有统计，没有第三方请求
- 令牌只存在浏览器 `localStorage`（可不勾"记住"，只留在内存）
- 所有请求只发往 `api.github.com`
- 可以只给细粒度令牌勾选指定仓库，把权限压到最小

### 11. 深色 / 浅色主题一键切换

右上角 🌙/☀️ 按钮切换主题，首次打开跟随系统偏好，之后记忆选择到 localStorage。浅色主题使用 GitHub 官方浅色调色板，卡片、徽章、日志、弹窗全部适配。

### 12. 一键导出扫描结果为 CSV

右上角 ⬇ 导出 CSV，包含所有 fork / 副本 / 自建仓库的完整信息：类型、仓库、上游、分支、状态、落后 / 独有提交数、推送时间、检测时间。文件带 UTF-8 BOM，Excel 直接打开不乱码，文件名自动带时间戳。

## 快速开始

### 1. 拿到文件

```bash
git clone https://github.com/<you>/fork-sync.git
cd fork-sync
```

或者直接下载 `index.html`。

### 2. 建一个令牌

**推荐细粒度令牌**：<https://github.com/settings/personal-access-tokens/new>

| 配置项 | 值 |
|---|---|
| Repository access | `All repositories`（要扫描全部就选全部） |
| Contents | **Read and write**（同步必需） |
| Workflows | **Read and write**（同步内容含 `.github/workflows` 时必需） |
| Metadata | Read-only（自动带上） |

保存后复制 `github_pat_...`。

### 3. 打开并扫描

双击 `index.html`（或访问 Pages 地址）→ 粘贴令牌 → 点 **扫描我的全部仓库**。

首次扫描 150 个 fork 约需 40–60 秒（每个 fork 2 次请求），结果缓存 10 分钟，之后再打开是秒开。

## 状态说明

| 状态 | 含义 | 可执行操作 |
|---|---|---|
| 已同步 | 与上游完全一致 | — |
| 可快进 | 落后 N 个提交，且没有独有提交 | 同步 |
| 本地领先 | 上游没有的提交 N 个 | — |
| 分叉 | 双方都有独有提交 | 手动 rebase / 建 PR（看差异） |
| 无法判定 | 上游已删除 / 无法比较 | — |
| 无关历史 | 与上游没有共同祖先（模板生成） | 不可合并 |
| 检测失败 | API 报错（权限、限流、网络） | 重新检测 |
| 同步失败 | 同步动作被拒（权限 / 冲突） | 修复后重试 |

## 工作原理

```
GET  /user                                   → 我是谁
GET  /user/repos?affiliation=owner&per_page=100&page=N
                                             → 全部仓库（分页）
GET  /repos/{fork}                           → parent / default_branch
GET  /repos/{upstream}/compare/{upBranch}...{owner}:{branch}
                                             → behind_by / ahead_by
POST /repos/{fork}/merge-upstream            → fork 快进（服务端完成）
POST /repos/{fork}/git/refs                  → 非 fork：打备份 tag
PATCH /repos/{fork}/git/refs/heads/{branch}  → 非 fork：强制指向新 HEAD
```

fork 的同步完全在服务端完成（等同 GitHub 网页上的 Sync fork），不需要 clone，也不需要本地提交历史。

## 常见问题

**Q：提示 `refusing to allow a personal access token to create or update workflow ... without workflow scope`？**

令牌缺 `workflow` 权限。细粒度令牌去令牌的 **Edit → Repository permissions → Workflows → Read and write**；classic 令牌去 <https://github.com/settings/tokens> 勾 `workflow`。改完立即生效，不用重建令牌。

**Q：只读检测不填令牌行不行？**

不行。扫描全部仓库需要认证（`/user/repos`），未登录只能看公开仓库。只读检测可以只给 `Metadata: Read-only`，但同步按钮会禁用。

**Q：为什么有些仓库显示「无关历史」？**

它们是从模板生成的（`template_repository`），GitHub 会压成一条全新的 `Initial commit`，与上游没有共同祖先，无法 merge。建议重新生成或忽略。

**Q：分叉的 fork 为什么不自动处理？**

双方都有独有提交时，任何"自动同步"本质上都是替你做强制覆盖。工具选择只展示差异，把决定权留给你。

**Q：关掉浏览器还会自动同步吗？**

不会。这是纯前端工具，没有后台进程。真要无人值守，用卡片上的「Actions」按钮复制一份 workflow 到仓库里，由 GitHub Actions 定时跑。

**Q：安全吗？令牌会不会被上传？**

不会。没有后端，代码里没有任何第三方域名，所有请求只发往 `api.github.com`。令牌保存在 `localStorage`，不勾"记住"时只存在内存里。建议用只覆盖必要仓库的细粒度令牌，并在不用时删除。

## 已知限制

- 浏览器关闭时不运行（无后台）
- 分叉仓库不做自动合并
- 非 fork 且有自己的提交时，会因为无法跨仓库比较而被归为「无关历史」
- 2000 个仓库以内无需改代码（分页上限 20 页）
- 首次扫描较慢，之后依赖 10 分钟缓存
